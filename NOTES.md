# Developer notes

The synthetic POSIX platform runs µOS++ applications as ordinary processes
on GNU/Linux and macOS. It is implemented by two packages:

- this package, `@micro-os-plus/architecture-synthetic-posix`, which
  provides the architecture instructions and the trace output channel;
- `@micro-os-plus/rtos-synthetic-posix`, which provides the µOS++ RTOS
  port (context switching, scheduler tick, and interrupts).

The first part of these notes describes this package; the second part
describes the RTOS port, for reference.

## This package

### Architecture instructions

The architecture headers are enabled only when
`MICRO_OS_PLUS_ARCHITECTURES_SYNTHETIC_POSIX_ENABLED` is defined. It will
be generated by the xcdl tool when that becomes available; until then, the
application must define it manually, preferably in
`micro-os-plus/project-config.h` or in
`micro-os-plus/architecture-defines.h`, both optional headers included by
`micro-os-plus/architecture.h` (`-D` on the compiler command line also
works).

In a hosted process, `nop`, `bkpt`/`brk`, and `wfi` are empty functions,
`data_barrier` is a sequentially consistent atomic thread fence, and
`instruction_barrier` is only a compiler barrier. The reasons are
documented in `instructions.h`.

### Trace

When `MICRO_OS_PLUS_DIAG_TRACE_ENABLED` is defined, exactly one output
channel must be selected, by defining either
`MICRO_OS_PLUS_DIAG_TRACE_POSIX_STDOUT_ENABLED` or
`MICRO_OS_PLUS_DIAG_TRACE_POSIX_STDERR_ENABLED`, preferably in
`micro-os-plus/project-config.h` or `micro-os-plus/diag/trace-defines.h`.
There is no default: the build fails if neither or both are defined.

The output goes through the standard I/O library (`fwrite()` followed by
`fflush()`), so that trace messages are correctly interleaved with the
application output (`printf()`, `std::cout`), even when the output is
redirected to a file or a pipe, and are not lost if the process crashes.
With STDERR, `stdout` is flushed before each message. To keep the trace
separate from the application output, select STDERR.

On bare-metal platforms the trace is initialised by the µOS++ startup
code. In a POSIX process the startup code belongs to the system library
and cannot be modified, so the initialisation runs as a constructor with
priority 101, the earliest available to user code. The priority is
honoured on ELF platforms (GNU/Linux) but ignored on macOS, where the link
order decides; therefore `write()` and `flush()` also perform the
initialisation themselves if it has not yet run. As a result, the trace
can be used from any static constructor, and applications must not call
`trace::initialise()` explicitly.

The standard I/O functions are not async-signal-safe, so the trace should
not be used from signal handlers, including code run by the RTOS clock
tick handler; the trade-offs are documented in `trace-posix.cpp`.

The trace channel is compiled only when the `diag-trace` headers are
available.

## The RTOS port

### Limitations

The µOS++ port for synthetic POSIX platforms is fully functional, except
that the scheduler runs in cooperative mode only; thread pre-emption might
be possible, but was considered not worth the effort.

### Context switching

Context switching is implemented with `getcontext()`, `makecontext()`,
and `setcontext()`, available on GNU/Linux and macOS.

### Scheduler tick

The scheduler tick is implemented with `setitimer()`, which delivers a
periodic `SIGALRM` signal (`ITIMER_REAL`). The handler is installed with
`SA_RESTART`, so system calls interrupted by the tick are restarted.

Interrupts are emulated by signals: critical sections block the clock
signal with `sigprocmask()`, and the idle thread waits for the next tick
with `pause()`.

### Startup

For portability reasons, execution starts in the `main()` function.

Static constructors are executed before `main()`, as usual, but their
order is not known, so the code must not depend on any specific order.

In particular, registry classes must rely on the BSS memory initialisation
to clear their data structures, and the registry constructor must not
clear them again, since by that moment other classes may have already
registered.

### Memory allocation

The default memory allocator uses the system `malloc()`.
